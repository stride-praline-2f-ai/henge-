## Implemented response and next evidence

1. Align Metal4 preflight with the existing decoder's deliberate no-op for exactly the observed four-byte compute-219 record. Other layouts/unknown records retain full fallback. This removes one avoidable cause of queue bridging without changing the reference decoder's semantics. No measured FPS/cooling claim.
2. Expand Settings log sharing to include current and previous app/native logs plus available profiler words. The missing previous-run files are now included by default when sharing. No new always-on diagnostic timer.
3. Reduce Metal4 CPU binding reset work: pooled argument tables now track exactly which buffer/texture/sampler slots were modified. New tables still initialize all 175 slots; reused tables clear only touched slots, including strides and explicit nil writes. The same real Metal table is submitted. A recording-table differential test covers 50,000 updates, boundary slots and empty reuse; actual FPS benefit remains unmeasured.
4. Keep high-risk TLB permission/invalidation checks; these logs do not justify bypassing them. Do not increase guest vCPU count or cache budgets blindly on the Duo, where physical compression is already high. Preserve current explicit user settings.
5. Validate the change with bounded malformed-stream/fuzz tests under ASan+UBSan, production Metal4 planner tests and device/simulator SDK typechecks in cloud. Native Metal4 execution on a paravirtual cloud GPU is not physical M4/A20 validation.
6. A crash diagnosis needs henge-prev.log and henge-native-prev.log from this export, plus the matching iOS Analytics termination report if available. No source-level change can reconstruct a SIGKILL/OS crash reason absent from app logs.
7. A useful Metal4 comparison must hold guest configuration, workload, LPM and cache warmness constant, switching only Automatic vs Compatibility graphics backend. Presentation-only MetalFX cannot cure CPU-side emulation cost. Prioritise safe engine reductions and cold-pipeline latency alongside backend parity; do not promise 60 FPS from a backend switch.

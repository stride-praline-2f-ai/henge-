## Candidates for a separate CPU build

- #218 (92c15ba2): genuinely new page-specific branch-fill history could avoid false remote-TLBI races. The fork already enables event waits and more conservative checked grouping. Adapt only the fill-history protocol with seq-cst publication, unknown/wrap/overwritten-log fallback and same-page rejection. Benchmark the extra hot-fill writes against saved acknowledgements, and compare range batching at32/256 pages. Do NOT import its VBLANK default: the macOS27 ABI uses event8 for disconnect; the fork deliberately does not emit it. Do not add another grouped-memory settings switch.
- #177/#186: segment-indexed block/exit ownership could reduce the full survivor scan. Latest capture attributes22.087s of25.619s direct eviction time to the block phase over109 evictions. Existing ring, batched publication, hot sysregs and timer paths already overlap these PRs; the O(segment) ownership redesign does not. It must preserve this fork's physical-page chain index, selective IJC retention, descriptor/front-cache lifetime, profiler lookup, full barrier and snapshot layout checks. A whole-branch cherry-pick would replace working custom architecture. Begin with stable bounded per-segment descriptor ownership and differential hash/index/SMC/poison/split/multicore tests, then measure compaction/repair cost. No uplift is yet claimed.
- #134: TLB-size comparisons could test cache locality, but every engine/assembly/bridge object must use the same layout and snapshot compatibility must reject mismatches. More RAM does not make a larger lookup table faster. Keep the established14-bit default until matched comparisons justify another value.
- #157: direct EL0 windows are still a prototype. They require coherent ASID/remap/permission/fault-handler/JIT-alias ownership; they cannot safely replace the tagged software MMU by flipping a flag. Shared-page retention also needs remap/ASID differential coverage.
- #214: pressure-driven balloon requests deserve a separate guest-driver/snapshot evaluation. Reject its silent-audio keep-awake loop as a desktop CPU efficiency change; it keeps a paused resident VM alive rather than reducing useful guest work and cannot guarantee OS background lifetime. Do not apply the8GB-device RAM cap to the16GB M4.
